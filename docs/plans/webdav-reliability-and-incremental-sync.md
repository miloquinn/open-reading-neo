# WebDAV 可靠性与增量同步重做计划

日期：2026-09-14。审计基线：`be343b4`。状态：调查与实施规划，未修改应用代码，未连接用户网盘。

## 1. 决策摘要

WebDAV 可以支持增量同步。现有元数据已经按记录增量传输；正文曾有分块方案，后来为云端直接可读的完整文件布局移除了它。当前故障不能简单归因为 WebDAV 做不了增量。

建议分两轮交付：先修现有协议的兼容性诊断、重复传输、失败恢复与迁移提示；再依据真实服务测试和云端文件使用需求，决定正文是否切换到分块协议。保留稳定书籍身份、阅读事件、业务适配器和本地恢复机制，避免再次同时重写所有层。

用户这次失败的根因仍待版本、网盘类型、报错与失败阶段确认。下文区分已验证行为和待验证风险；模拟服务结果不代表坚果云的实际行为。

## 2. 代码与实验发现

### A. 连接成功不代表同步可用：已复现

`lib/services/sync/webdav_client.dart` 的 `testConnection()` 检查 OPTIONS、建目录、普通 PUT/GET/DELETE，没有验证真正同步依赖的条件写入。

`lib/services/sync/storage/webdav_sync_storage.dart` 的 `_write()` 对所有写入调用 `verifyMutableWritePreconditions()`，要求 `If-None-Match` 和过期 `If-Match` 都返回 412。创建元数据批次也经过这个入口。`capabilities.strongVersions` 则直接返回 true，并非实测结果。

临时 HTTP 适配器实验：同一个客户端连接测试通过，随后创建 `sync/metadata/devices/a/changes/000000000001.json` 因服务器忽略 `If-Match` 而返回 unsupported。实验没有调用 TXT 同步。

这是能力验证与产品入口不一致。不能通过删除检查、无条件覆盖共享文件来修复；现有协议的 `head.json` 和正文提交仍依赖版本保护。

### B. 正文没变化也完整下载：已复现

`book_content_sync_service.dart` 的 `_reconcileBook()` 先查询 current/head，再无条件调用 `_readRemote()`；后者下载整个 current，之后才比较本地、远端内容哈希。

临时计数存储实验：首次同步完成后，不修改任何内容，再次 reconcile；结果为 uploaded=0、downloaded=0、failed=0，但底层调用一次完整 current.txt 下载。计数表示业务状态变化，没有反映实际网络传输。

这会增加耗时、带宽、临时磁盘使用和移动端被挂起的概率。启用正文自动同步时，调度器前台默认每 45 秒触发检查；实际频率还受执行时长、合并与失败影响，不能理解为每本书必定每 45 秒下载一次。

### C. 修改后的传输成本远大于改动：代码确认

`_push()` 为新版本依次执行：创建完整 history 并下载校验、写入完整 current 并下载校验、写入并校验 book.json。

在历史不存在的正常发布路径中，大小为 N 的新正文，仅 history/current 就涉及约 2N 上传 + 2N 下载；更新已有书籍时，前面的远端对账还会下载旧正文。来源附件与 HTTP 开销另计。当前 `uploadedBytes` 返回 snapshot.size，不能作为真实网络字节数。

例如 100 MiB 的新正文，即使只改几行，发布步骤也可能传输约 400 MiB，而不是那几行；这不是实测网盘速度。

### D. 旧云目录不读取：代码与现有测试确认

当前引擎入口是根目录 `format.json`、`sync/metadata/devices`；正文是 `books/.../current`、`book.json`。旧 v1/v2/v3 对象不进入当前协议读取路径。

`test/sync_engine_storage_test.dart` 明确验证旧对象保持原样。保留旧文件不等于迁移旧数据。新旧客户端混用，或新设备只有旧云备份时，可能各自成功却看不到另一套数据。

### E. GET 强 ETag 要求比连接测试更严格：代码与现有测试确认

`getTextWithVersion()`、`downloadWithVersion()` 要求同一次 GET 响应携带强 ETag。HEAD/PROPFIND 有 ETag，而 GET 没有或只有弱 ETag，也会失败。当前 storage.readText 对不可变元数据和共享可变正文一视同仁。

正文需要绑定同一次读取的版本，不能在下载后补一次 HEAD 并将其版本冒充正文版本。不可变对象可以另行设计内容哈希校验，但必须同时调整协议与存储契约。

### F. 需要继续实测的因素

- OPTIONS 被限制、HEAD 不支持、目录响应格式、同源重定向、中文路径、限流、上传时间与弱网。
- 当前基础请求助手支持同源重定向，但带版本的 GET/流式 PUT 路径关闭自动重定向；可能形成连接测试与实际读写差异。
- 连续日志按序读取，一个缺失或损坏批次会中断本轮；不能直接跳过并推进游标，否则会丢操作。
- 部分非进度元数据仍在扫描发现变化时生成 HLC，发现时间不等于编辑时间。阅读进度已有专门事件语义，不能一概改成“最后上传获胜”。
- 元数据与文件分别记录失败，但 `syncNow()` 和自动周期仍先 await 元数据成功；并非所有失败都已实现任务隔离。
- 自动同步重试退避可能被定时 poll 的 immediate 请求打断，应按错误类别建立统一的下一次允许尝试时间。

上述因素需要对应的请求记录或故障注入验证，尚未认定为本次用户故障。

## 3. 增量应做到哪一层

| 行为 | 当前状态 | 目标 |
| --- | --- | --- |
| 阅读进度、笔记、设置变化 | 元数据批次 + 游标，已有增量 | 保留；阅读变化不能引起正文网络传输 |
| 两端正文均无变化 | 不重复上传，但仍下载整本 | 只检查版本/清单，正文上传下载均为 0 字节 |
| 新增章节或局部编辑 | 新正文完整传输且重复保存/校验 | 分块时只传缺失或变化块与清单 |
| 新设备首次下载 | 必须取得所需内容 | 完整恢复所需块；这是首次下载，不是增量失效 |
| EPUB/PDF 等原文件 | 整文件版本 | 第一轮保持整文件，避免把 TXT 差分机制泛化到所有格式 |

普通 WebDAV 的 GET/PUT 没有跨服务商通用的任意字节修改、服务端拼接保证。客户端可以把 TXT 切为块，只上传新块，接收端重组完整 TXT；因此“WebDAV 不能增量”不成立。

但“云端每次都有最新完整 TXT，可被其他软件直接打开”和“只上传新增字节”不能在普通 WebDAV 上同时无条件保证。重新生成云端完整文件一般仍需要完整上传，除非目标服务提供并验证了扩展能力。必须把这个取舍讲清楚。

## 4. 第一轮：修复现有协议并建立证据

### P0：诊断、连接验证与旧数据发现

1. 每轮生成 run_id；记录 App/协议版本、同步空间指纹、阶段、HTTP 方法/状态、耗时、实际字节数、重试、失败类型。路径按需脱敏，不包含凭据、书籍正文或笔记。
2. 连接配置页区分“基础连接可用”“当前协议元数据可用”“正文双向更新可用”；测试与运行复用同一能力判断，分别显示失败原因。
3. 能力结果按服务器、账号、根目录缓存，并区分不支持、未验证、暂时失败；权限/网络错误不能永久记成不支持。
4. 扫描已知旧目录并提示版本和迁移路径，禁止把“发现旧备份”显示为“空云端”。先列出可恢复数据数量，不自动删除旧内容。
5. 界面分开显示已上传云端、已下载本机、等待另一设备上线、正文未下载、冲突与失败。不能知道离线设备是否已收到时，不宣称“所有设备同步完成”。

验收：模拟服务可准确区分 401/403、429、507、5xx、超时、GET 弱/无 ETag、忽略条件请求；诊断可直接定位失败阶段。真实服务执行同一探针，输出兼容性记录。

### P1：无变化不传正文、独立任务与可恢复提交

1. 使用已验证的 current/head 版本、本地正文修订号及来源资料修订，建立无变化快速路径；有未完成提交、文件缺失或冲突时不走该路径。
2. 应用内编辑生成持久修订与待上传任务；外部文件变更通过文件状态检测与必要的重新哈希对账。不把不可靠的 mtime 当作唯一内容证据。
3. current/head 任一版本改变时，只下载必要对象；必须保留外部云端编辑检测，不能只看 book.json 而忽略 current。
4. 每个任务独立持久状态与重试，连接认证/空间不匹配等全局错误统一阻止写入；单本正文失败不阻止无依赖元数据。正文描述仍需正文提交校验完成后才能发布。
5. 恢复已提交的中间状态，防止每次重试重传完整历史；准确计量 history、current、校验回读与重试流量。
6. 不直接去掉校验来减少流量。优先跳过已验证且版本未变的对象，再评估可靠服务端 COPY 等可选优化；所有服务均有正确的默认路径。
7. 调度器遵守 Retry-After 和退避期限，降低重复目录创建、重复能力探测及不必要轮询。

验收：两端静止的已同步书籍，连续检查正文上传/下载均为 0；只翻页时正文传输为 0；单本失败时无依赖元数据成功；每个提交阶段中断后均可恢复。

### P2：现有空间迁移

1. 区分已有本机数据、旧云端备份、新云端空间；以 book_uid/历史身份映射去重，保留删除与冲突语义。
2. 旧协议仅用于明确的一次性导入，迁移落点仍使用当前协议；迁移过程持久化且可以重试。
3. 新旧客户端混用明确提示互通边界，不长期偷偷双写两套协议。不同空间不得复用游标或完成标记。
4. 新空间检验完成前保留旧空间；新设备仅有旧云备份的恢复也必须覆盖。

## 5. 第二轮：正文增量与更宽的服务兼容性

进入条件：完成 P0/P1，拿到真实服务能力结果；明确云端完整 TXT 是否需要每次即时更新。建议以 App 内可靠增量为主要目标，完整 TXT 作为明确可见的导出功能；若必须即时兼容其他阅读器，就接受完整文件传输成本。

### 目标协议

- 元数据继续使用独立事件/记录与稳定身份，SQLite 保存 outbox、远端游标和待物化记录。
- TXT 以不可变块、不可变修订清单为事实来源。清单记录 book_uid、revision_id、父修订、设备、编辑时间、编码、块顺序、总大小和整书哈希。
- 优先验证内容定义分块，避免在文件前面插入几字导致后面所有固定块失效；章节信息作为编辑定位辅助，不能只靠章节标题认定身份。
- 块和清单都具备完整性验证，发布顺序为块完成并确认 → 清单 → 提交记录。不可见/未完整的提交保留待办，不提前确认本机已同步。
- 中断后复用已确认块。新设备按清单流式恢复，校验后原子替换；保持原编码字节与现有定位恢复规则。
- 并发修订按父子关系判断：后继正常前进，互不继承则保留双方；时间只能辅助推荐。进度保留回读与并发事件语义，删除必须传播 tombstone。

### 不支持强条件写入的服务

不能把当前共享 current/head 协议简单切成无条件 PUT。若真实服务确实缺能力，需要为其验证只追加的协议：设备会话使用随机、互不覆盖的命名空间，发布唯一不可变批次/修订，目录与提交记录用于发现，内容哈希用于验证。共享 latest/head 只能作为可重建提示，不能作为唯一事实。

这条路线还必须解决完整目录列举、延迟可见、下载到半个文件、设备备份克隆、并发重试、损坏提交和首次空间创建竞争。没有验证这些条件，就不宣称兼容所有 WebDAV。网络临时失败不能触发协议自动切换；迁移应是明确的空间级操作。

### 可读文件与历史

若采用分块事实来源，完整 TXT 导出必须标注对应修订与更新时间；导出失败不能抹掉已经成功的同步状态。共享可读导出仍需条件写入，或使用各修订独立文件名，不能因“只是导出”就无条件覆盖用户云端编辑。

不恢复长期并存的 V1/V2/V3 写入模式。历史分块方案只作为经验与夹具来源，不能把其旧测试指标当作当前实现能力。

先保留完整历史引用，之后单独引入快照和垃圾回收。回收必须基于可验证快照、设备确认与保留期；长期离线设备回归需重新基于快照对账，不能靠删除日志缩小目录而丢 tombstone。

## 6. 验收矩阵与交付顺序

| 层次 | 必须验证 |
| --- | --- |
| 协议 | 双设备离线/并发、编辑与删除冲突、回读、重复投递、乱序发现、缺块/坏批次、断点恢复、旧空间迁移 |
| HTTP | 真实 HTTP 服务 + 故障代理；ETag/条件请求各能力组合；限流/超时/目录格式/中文路径/同源重定向 |
| 性能 | 无变化 0 正文字节；单次阅读进度不传正文；200/500 MiB TXT 局部编辑、开头插入、追加章节；记录实际总上传下载及请求数 |
| 分块目标 | 对约定的大文件小改动夹具，新增正文块传输应显著小于全书，目标低于全书 1%；单独列出清单和验证开销，不能只统计有效载荷 |
| 实机 | iOS + Android 双设备；锁屏/切后台/杀进程/重启/切账号/弱网；校验进度、正文和书架最终一致 |
| 服务 | 优先用户实际服务；另验证坚果云、Nextcloud、群晖或用户 NAS，并记录版本及配置 |
| 产品构建 | 与核心回归、stateful widget tests 分开执行和报告；按仓库规则隔离进程 |

交付顺序：诊断与能力一致性 → 无变化快速路径与恢复 → 旧空间迁移 → 真实双设备试用 → 分块原型基准 → 正式协议迁移。每步都有独立回归与回退点，先证明上一层可靠，再扩大范围。
